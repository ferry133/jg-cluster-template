# 執行順序：以「一台 appliance 到零 IT 客戶手上」為唯一目標

2026-08-20 重排，同日依 ferry133 裁定再收窄一次（備份與交接一併延後）。五個 change 同時開著的時候，每一個都在等別的那個，而沒有任何一個
在往出貨走。這份文件只決定**順序**，不重述任何工作項——工作項的唯一副本在各 change
自己的 `tasks.md`，這裡只指名編號。

> 引用工作項一律寫成 `<change> <編號>`。五個 change 都從 1 開始編號，單獨一個
> 「8.3」指不出是哪一個。

**目標句**：客戶收到一個紙箱，做三個物理動作，系統就會動，而且之後我們支援得了它。
一件事在不在關鍵路徑上，就問它擋不擋這句話。

## 標記法

每一個未完成工作項都在自己的 `tasks.md` 裡帶著相位標記，整節同一個處置的標在 `##` 標題上。
標記與這份文件是同一個判斷的兩個位置——**改了一邊要改另一邊**。

| 標記 | 意思 |
|---|---|
| `**[P1]**` | 零 IT 客戶支援，現在在跑的 |
| `**[P2]**` | provisioning 自動化（`factory-agent`） |
| `**[延後：備份]**` | 2026-08-20 裁定延後，條件是短期內無客戶交付 |
| `**[延後：交接]**` | 同批延後 |
| `**[延後]**` / `**[擱置]**` | 不在出貨路徑上；理由與接受的風險見下方擱置表 |

已完成的項目不標——歷史不需要相位。

## Phase 1 — 零 IT 客戶支援（新的第一優先）

`zero-it-onboarding` 從隊尾移到隊首。理由不只是排序偏好：**它持有解開別人的鑰匙。**

`deployment-profiles` 5.7（D45）——每一台 appliance 都會帶著一個永遠紅的健檢出廠，
而那個健檢同時扣著 dead-man switch——D45 的裁定是「先不改檢查」，因為三個修法裡唯一
不會把真實偵測換成裝飾的那個，**要等 `zero-it-onboarding` 1.4 的機制先存在**。
所以先做 zero-IT，5.7 才有得解；反過來排的話它會一直卡著。

順序：

1. **`zero-it-onboarding` 1.1–1.5**（spikes）。其中 **1.4 是槓桿點**：能不能在沒有 App
   的情況下，讓客戶用手機瀏覽器回報 rebinding protection 的偵測結果。
2. **`deployment-profiles` 5.7**，用 1.4 的結果收掉永遠紅的健檢。同一件事在
   `zero-it-onboarding` 5.4 被標為阻塞項——一起結案，不要兩邊各記一次。
3. **`zero-it-onboarding` 5.1–5.3**（出貨形態）。Talos 預裝內碟、ISO/schematic 內嵌
   SideroLink join token、插電自行回連。這三項才讓「三個物理動作」是真的而不是說法。
4. **`zero-it-onboarding` 4.6–4.7**（紙本產出流程、箱內 QR）。紙本要與
   `README-zero-IT.md` 同源——客戶讀它的時候網路還沒通。
5. **`deployment-profiles` 8.6** —— appliance profile 必須**在 appliance 上實跑到工作負載
   就緒**，不得只驗 `task configure` 的輸出。那四道渲染期缺陷全部無聲通過了
   `task configure`（D14）。這驗的是叢集會動；下一項驗的是人做得到。
6. **`zero-it-onboarding` 8.1–8.4**（未受訓讀者實測）。**這才是 zero-IT 的驗收**，
   不是 8.5 的第一台真實客戶。沒有人在旁邊的情況下走不完，就還沒做完。

`zero-it-onboarding` §6（LINE bot）與 §7（現場診斷）**不在 Phase 1**：它們是支援機制，
第一台可以由人接。§7.1（列舉「只有站在客戶網路裡才答得出來」的問題）例外——它是分析，
不是實作，而且 1.4 需要它的結論。

## Phase 2 — provisioning 自動化（`factory-agent`）

**盡可能自動化**。手工跑一次是為了讓 runbook 的指令與斷言先被人校正過，不是終點——
7.2（人工照 runbook 跑完）之後緊接 7.3（交給 agent 跑同一份，比對結果一致），這兩項
是同一件事的兩半，中間不要停。

在範圍內：

- §2 factory 執行環境（jg-base + jcom）
- §3 工單狀態機——沒有它，中途斷掉就得靠人回想走到哪
- §4 provisioning 流程：機器註冊偵測、Omni cluster 建立、repo / tunnel / DNS 決定性命名、
  `cluster.yaml` 由 Omni 回報的實際網路狀態推導、`task configure` → push → bootstrap、
  「先查後建」的重跑安全、QUIC 封鎖自動修復、未知失敗停下來升級而不是無限重試
- §5 身分與憑證，扣掉交接相關的 5.0b / 5.5
- §7 runbook 與 skill：7.2 → 7.3 → 7.4
- §8 驗收 8.1–8.4、8.6（8.5 要有真實客戶，見下）

**與 Phase 1 的關係**：大致獨立，可重疊。唯一的方向性依賴是
`zero-it-onboarding` 5.1–5.3（Talos 預裝、ISO 內嵌 join token、插電自行回連）餵給
`factory-agent` 4.1（機器註冊偵測）——機器不會自己回連，就沒有東西可以偵測。

## 擱置

擱置要寫下**接受了什麼風險**，否則它與「忘記了」讀起來一模一樣。

| 擱置的東西 | 理由 | 接受的風險 |
|---|---|---|
| `reconcile-jcom-lineage` 全部（17 項） | jcom 是 factory 的落腳處與血脈同步對象，不在「箱子到客戶手上」的路徑上 | jcom 繼續無法接收模板更新，分岔繼續擴大。時間成本會漲，但不擋出貨 |
| `agent-state-portability` 全部（29 項） | 它整個 change 就是備份範圍的擴張，隨備份一併延後 | **客戶機器全損時，agent 的 session 歷史與 memory 不在任何備份裡**，只能重建出「半個 agent」——看起來還記得，實際上少了三個月。交接封裝也延後了，所以這件事目前**沒有任何地方寫給客戶看**，只記在這裡 |
| **備份，全部**：`deployment-profiles` 7.7 / 8.3b / 8.3c / 8.5 | 2026-08-20 由 ferry133 裁定與交接一併延後。**條件**：短期內不會有客戶交付，所以「帶著壞掉的備份出貨」這個風險目前不成立 | 事實記在這裡，不必再問一次：8.3c 的 prune 每天刪掉當日以外的全部（影響的是既有叢集 jg-jiahd／jcom／jgt-appliance，不是未來的客戶）；7.7 的 MariaDB（jcom freepbx，已 92 天）不在任何 dump 路徑上；8.3b 那組曾以明文出現在 ConfigMap 的 R2 憑證仍然有效；8.5 的 spec 與實作互相矛盾，兩邊都宣稱自己是對的 |
| **交接給客戶**：`factory-agent` 5.0b / 5.5 / 7.0 / §6 全部 | 2026-08-20 同批延後。交接是服務結束或客戶要鑰匙時才發生的事，第一台上線時還不需要 | 「客戶隨時能拿回鑰匙」在交接封裝寫出來以前仍然只是口頭承諾。`age.key`、GitHub repo、Omni 控制權、Cloudflare 帳號分散四處，沒有任何一個動作能把它們一起交出去 |

**擱置不等於關閉。** 上面每一項的工作項都留在原本的 `tasks.md` 裡沒有被刪，各 change
的 `proposal.md` 與 `design.md` 也沒有改——重排的是執行順序，不是判斷。
